# Developer experience, diagnostics and the error model

[Master specification](README.md) · [Independent review](../reviews/independent-review-candidate-1.md) · [Operations](22-application-operations-and-services.md)

**Status:** REVIEW CANDIDATE 2. Architectural direction adopted from the independent review (H3, H4, M3, M8); numeric budgets are PROPOSED targets; all claims remain VALIDATION REQUIRED. This specification does not authorize implementation planning.

Rjango's primary audience is experienced Django developers who do not yet know Rust. The framework must let them become productive before they master Rust, without hiding ownership, error, async, transaction or I/O semantics. Each abstraction should teach the relevant Rust concept at the point it is needed, and compiler output must stay readable when it does.

## Rust concepts the framework teaches

| Rust concept | Where a Django developer meets it first | How Rjango teaches it rather than hides it |
| --- | --- | --- |
| `Option` vs `Result` | `find(pk)` vs `get(pk)`; `first()` vs `require()` | Distinct names, and documentation pairs each with its Django equivalent and the point where the analogy stops. |
| `?` and error conversion | Every handler | One framework error type at Tier 0; domain error enums at Tier 1 (see the error model below). |
| Moves and consumption | `venue.edit()...save()`, `tx.commit()` | Consuming methods make use-after-save or use-after-commit a compile error with a Rjango-specific explanation. |
| Exclusive borrows (`&mut`) | Transaction queries | "One connection does one thing at a time" is enforced by the type, not by a hidden lock. |
| Enums and exhaustive `match` | `Patch<T>`, `Decision`, relation states, commit outcome | Framework enums are small and documented, with `match` examples. |
| Traits and bounds | Field types (`DatabaseValue`), response types | `#[diagnostic::on_unimplemented]` messages state what to implement or derive. |
| `async`/`.await`, `Send` | Every handler on the multi-thread runtime | Handler macros assert `Send` and explain the usual causes (holding `std::sync::MutexGuard` or `Rc` across `.await`). |
| Capability by parameter | `ctx.db()`, synchronous hooks without context | What a function can do is visible in its signature; hooks cannot use framework I/O because they receive no handle (foreign blocking I/O is an anti-pattern flagged at runtime, not a compile error). |
| Shared state (`Arc`) | Application state | `.state(T)` registration with `T: Send + Sync + 'static`, extracted by `State<T>`. Mutable shared state uses explicit `Arc<Mutex<_>>`, atomics or framework primitives, taught as a deliberate step. "No `Arc`/locks for developers" means none for framework-managed resources, not none ever. |

Lifetimes should not appear in Tier 0 user code. Framework handles are owned, cheaply clonable values; borrowed lifetimes appear only in Tier 2 APIs and escape hatches.

## Diagnostics contract

1. **Trait messages.** Every user-facing trait carries `#[diagnostic::on_unimplemented]` with a message, a label and a link to `rjango explain`. Internal blanket impls use `#[diagnostic::do_not_recommend]` so rustc does not suggest framework internals.
2. **Handler argument checks.** Route, operation, job, listener and policy macros emit a separate assertion for each argument, spanned to that argument: an extractor must implement the required trait, and the body extractor must come last. Axum's whole-function `Handler<_, _>` error must not be the first error a user sees.
3. **`Send` assertions.** Macros assert that the generated future is `Send` and point to Rjango guidance. Validation question: whether the span can identify the offending `.await`.
4. **Extension model.** Users write policies, listeners, hooks, validators and admin actions as annotated functions, not as implementations of async traits. Backend traits (cache, storage, email, queue) declare `Send`-bounded futures in their signatures, so implementors do not hit missing `Send` bounds.
5. **Error-tolerant macros.** On invalid input, a macro emits `compile_error!` *and* a best-effort expansion, so generated items such as `Venue::F`, `Venue::R` and `NewVenue` still resolve in rust-analyzer. Validation: does completion survive a malformed attribute?
6. **No deep type-state in user-visible types.** Public result types are shallow (`Loaded<M>`, `Page<T>`), so compiler output does not print nested generic types.
7. **Honest classification.** Each check is either a compile error (single-type, macro-visible) or an AMG validation error (cross-type, reported at startup and by `rjango check` with source spans). Specifications must not promise compile errors for cross-type checks.
8. **Generated items are documented.** Rustdoc shows generated public items with "generated by `#[rjango::model]` on `Venue`" and a link to the declaration. `rjango expand <item>` shows the generated code.
9. **Messages are API.** Compile-fail snapshot tests (trybuild) cover the twenty most common mistakes per macro. Message text is reviewed by developers new to Rust, and changing it is an API-impact item in the changelog.

## Error model

**Tier 0:**

- Handlers return `rjango::Result<T>` (`Result<T, rjango::Error>`).
- `rjango::Error` carries a stable code, a Problem Details type, an HTTP status hint, safe detail and a private cause chain.
- `.context("...")` adds private diagnostics.
- `?` converts database, validation, policy and framework errors automatically.

**Tier 1:** domain errors are enums with a derive (illustrative: `#[derive(rjango::Error)] enum CreateVenueError { #[problem(status = 409, code = "venue.slug_taken")] SlugTaken }`). They convert into `rjango::Error` via `?`, and their variants become AMG error descriptors for OpenAPI, the TypeScript SDK and MCP.

**Mapping rules:**

- Status codes are assigned at the adapter boundary, not in data code.
- A scoped lookup that finds nothing is 404 whether the row is absent or hidden by policy, so existence does not leak.
- `NotFound` for a *referenced* identifier inside command input maps to 422 with a field error, not 404.
- Unique and foreign-key violations map to field errors through constraint metadata ([03](03-models-and-orm.md)).
- `CommitOutcomeUnknown` maps to 503 with a retry-after and an idempotency hint.
- Panics in handlers are caught at the adapter, logged with the correlation ID, and return 500 Problem Details; the process continues.

Wire formats follow [RFC 9457](06-http-and-routing.md). CLI and MCP render the same descriptors.

## Development loop

**Budgets (PROPOSED, VALIDATION REQUIRED).** The reference application has 30 models, 100 routes and 10 jobs on documented reference hardware. Targets are measured with incremental `cargo` builds in the default dev profile, from save to serving:

- Change inside a handler body: ≤ 5 s.
- Model field added: ≤ 15 s.
- Clean dev build: ≤ 3 min.

Generated code per model is budgeted and measured in CI. Each budget regression is an API-impact item.

**Crate layout.** New projects are one crate. The guide documents splitting apps into workspace crates when rebuild budgets are exceeded; app registration and AMG identities do not change when an app moves into its own crate.

**Introspection mode.** The application binary supports a metadata-only mode, invoked by the CLI, that builds and validates the AMG, writes canonical JSON and exits. It connects to no database, broker or external service, and it loads no secrets. `migration make`, `inspect`, `openapi`/`client generate`, `rjango check` (static portion) and development MCP resources use it. A compile failure blocks these commands, as an import error blocks Django's `makemigrations`; the CLI then reports the compile error rather than a generic failure.

**Dev server.** `rjango dev` watches sources, rebuilds, and restarts the server process after a successful build. The old process keeps serving until the new one is ready. After a failed build it keeps the old process running and shows the error in the terminal and in an HTML error page. The server reruns in-process AMG diffs on each rebuild and reports affected projections, as in the "Development Hot Reload" sketch in [02](02-application-metadata-graph.md). Live code patching is not promised.

**Shell.** Rust has no practical REPL, and the Django `manage.py shell` analogy stops here. Rjango provides:

- `rjango db shell`: a SQL console against an explicitly selected environment. It is refused in production unless an audited break-glass policy allows it.
- `rjango run <script>`: compiled scripts in `scripts/` with the app prelude, a context and an explicit identity, reusing the incremental build cache.
- `rjango inspect` and AMG queries for structure.

The Django guide teaches these as the replacement workflow.

**Version skew.** The `rjango` facade, macros and runtime crates are published in lockstep with exact-version dependencies. The runtime declares a Cargo `links` key, which Cargo requires to be paired with a trivial build script, so that two runtime versions in one build fail at dependency resolution with a clear message, rather than as type errors like "expected `rjango::Db`, found `rjango::Db`". Macros resolve the facade crate's actual name in the user's `Cargo.toml` (for example with `proc-macro-crate`), so `rj = { package = "rjango" }` works. Generated code then reaches everything else through that crate's hidden `__private` module ([05](05-app-system.md)). A hard-coded `::rjango` path would break renamed dependencies.

**MSRV and edition.** Rust 2024 edition; MSRV is at least 1.85 (async closures for `db.atomic`). The MSRV policy itself remains open in [21](21-design-backlog.md).

## Validation required

- Usability study with Django developers who do not know Rust: concepts, compile errors met, time to a tenant-scoped CRUD endpoint with admin and test.
- Rebuild times against the budgets.
- `Send` span quality.
- rust-analyzer behaviour on macro errors.
- trybuild message review by newcomers.
- Introspection mode with no network access.
- `links`-based skew detection across renamed and workspace dependencies.
